1. How to read this

This is the same IA surface as IA-01, repurposed as the tracker. The nav on the left is the locked eleven-item architecture, and every item now carries a status light and a route count. Click any item to see the routes inside it, each one marked shipped, WIP, partial, open or retiring, with its provenance: whether the route exists in shipped code, exists only as a locked design, or is net-new and unbuilt.

The filter in the bar above scopes the route lists. It opens on Closed and WIP, which is what this round was asked to populate first. Two modules sit outside the eleven nav slots and are reachable from the mock chrome: Home is the app-name row at the top of the sidebar, and Notifications is the header bell.

Each module leads with Screens and files, the real artifacts on disk, locked ones first. Anything the browser can render carries a Preview button that opens the actual screen inline, so the locked create-plan screen is one click from its status rather than a filename you have to go hunting for. Open sends it to its own tab. Below that sits that module's Backlog, and the Backlog and docs tab gathers every backlog item in one table. Section 8 says where to edit when something changes.

3. The Orders split

Orders was one nav item doing three jobs. The split follows team ownership rather than data shape, which is what the 2026-07-27 pivot settled: Customer Success works deliveries, Operations works supply, and chasing money keeps its own owner. Three destinations, one lineage.

Orders CS

Every individual delivery, recurring and one-time. Three tabs replace the current single flat list: Upcoming, Delivered, Needs attention. One-Time Orders folds in as a filter rather than a sibling item. This is the only screen where a delivery is rescheduled.
  • Absorbs /one-time-orders
  • Owns the reschedule action outright
  • Carries a contract-state chip per row

Payment Reminders CS

Structurally a filter on Orders, kept as a screen by explicit decision twice over, because chasing money is a distinct job. The change needed is of kind, not position: it is a reminder-job log today and has to become a work queue sorted by urgency with a send action on the row.
  • Route unchanged, screen rebuilt
  • Reminder counts as a fraction of the dunning cap
  • Cap read from Settings, Payments

Inventory Ops

Forward demand built from contracts and dates StackBack already holds. Dashboard first, not a flat table, because the question is whether a shortfall is coming. Renamed from Forecast so the label matches the word a merchant reaches for.
  • Entirely net-new, nothing in code
  • Replaces the Holds screen
  • Owns the out-of-stock policy config
The split leaves one boundary undefined, and it decides two screens. Orders is scoped paid-only for Customer Success, but a PAYG delivery awaiting payment is not yet paid. Either it appears in Orders as an unpaid upcoming row, in which case Orders and Payment Reminders overlap and the paid-only rule is not real, or it lives only in Payment Reminders until payment clears, in which case a rep looking at Orders cannot see a delivery that is about to happen. Both readings are defensible and they build different screens, so this is the first thing to settle next round.
Holds was locked and then superseded inside the same day, and the tracker follows the later call. The morning of 2026-07-27 locked an out-of-stock spine with a Holds screen and Hold-until-stock-is-back behaviour. IA-01, written that evening, removed Holds on the grounds that StackBack cannot read Shopify stock levels and only discovers a shortage when a push fails, so a hold state it cannot detect is not implementable. This tracker follows IA-01 and shows no Holds screen. Worth confirming rather than inheriting, because six wireframe iterations were built on the earlier reading.

4. Notifications, two lanes

Notifications is one word covering two unrelated systems with different audiences, different delivery paths and different homes in the nav. The repo already separates them: the Linear QA label set carries Admin Notification and Customer Notification as distinct labels, so the tracker adopts that vocabulary instead of inventing a third name.

Admin Notification Ops Partial

Alerts to the merchant. A daily glance, not a destination, so it lives in the header bell on every screen rather than taking a nav slot. The route exists in the backend with no designed screen. INT-01 is in review.
  • /notifications centre, backend only
  • Delivery config to Settings, Admin alert delivery
  • Severity tag and action-required flag already in code

Customer Notification Platform WIP

Messages to the customer, on email and WhatsApp in parallel. Set at onboarding and rarely touched after, so it moves inside Settings. The editor still opens as a full page because it carries an editor, a live preview and a test send.
  • Ten canonical templates, down from fourteen
  • Email via SES, WhatsApp via Meta Cloud API
  • Content phase is the open work

The bell itself Open call

An embedded app cannot add anything to Shopify's own top bar, so a bell needs StackBack's own header row inside the content frame. That is persistent chrome on every screen and it costs vertical space everywhere.
  • Option A, keep the bell, pay the chrome
  • Option B, no bell: a Home card plus a banner on the screen each alert concerns
  • Needs an App Bridge check before either is committed

6. What is new since IA-01

IA-01 settled the shape of the nav. This revision does not move any of the eleven items. It adds the tracking layer, the route trees inside each module, and the ownership column.

1

Routes, not just items

Every module now lists the routes inside it, taken from the shipped build where they exist rather than described from memory. A route count is tracked, and each one carries a provenance mark so a net-new proposal never reads as an existing screen.

2

Ownership as a first-class column

The Orders split was decided by team ownership, so ownership is recorded per module and per route. It is what makes the Orders, Payment Reminders and Inventory boundary reviewable instead of a matter of taste.

3

Status that cannot drift silently

Counts in the bar and in the rollup table are computed from the route data, not typed. Change a route status and every total moves with it, so the tracker cannot claim a coverage it does not have.

Provenance is marked because two of these modules are mostly invention. Inventory has nothing in code at all and Payment Reminders has a route but no designed screen, so most of what those two sections show is proposed rather than observed. Everything drawn from the shipped build is marked "In code", everything from an approved spec is marked "Design locked", and everything proposed here is marked "Net-new". Read the net-new rows as questions.

7. Reference shelf

The cross-cutting documents that do not belong to any single module. The IA decision record, the code-grounded screen map, and the codebase analysis every route in this tracker was checked against.

8. Keeping this current

Everything on this page renders from two maps near the top of the script, under a comment banner that reads EDIT HERE. Nothing else needs touching, and no counts need updating by hand because every total on the page is computed.

1

To add a backlog item

Find BACKLOG, find the module key, add one line: B('what to do','open','why or who blocks it'). State is one of open, gated, parked or bug. It appears on the module card and in section 3 at once, and the counts move themselves.

2

To add or relock a file

Find FILES, add F('/Design/…','Label','locked','note'). Paths start from the stackback folder. When a new version supersedes an old one, change the old entry from locked to ref rather than deleting it, so the lineage survives.

3

To change a status

Route statuses live in each module's routes array as the third argument. Module-level status is the status field. Change either and the sidebar lights, the rollup bar and the section 2 table all follow.

This page has to be served over HTTP, not opened as a file. Two reasons. The Polaris screens load their components from a CDN and render as dead static snapshots under a file path, which is already written down in the Polaris README. And the inline previews here are iframes pointing at sibling folders, which a browser blocks under file access. Serve the stackback folder and open this at /merchant/IA_MerchantAdmin_v2.html.
