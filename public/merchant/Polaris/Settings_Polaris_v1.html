The route

What the URL tree looks like before and after. The twelve-item nav does not move: every change is inside Settings, plus one card on the three storefront items. Green is added, struck through is removed.

Today, in the shipped build

/app/settings flat, five tabs, no search   tab order-placement   tab timing-configs   tab cancellation-policy   tab brand-settings logo + 2 colours only   tab shipping-zones /app/widgets/:templateKey 48 controls /app/portal-settings/customize 33 of them again /app/landing-pages/customize/:id/... per page /app/integrations /app/custom-checkout-adapt

After, grouped rail plus search

/app/settings redirects to the first group   /app/settings/branding 17 tokens + status + portal chrome   /app/settings/selling 19 settings   /app/settings/orders was tab order-placement + timing   /app/settings/payments   /app/settings/shipping was tab shipping-zones   /app/settings/policies was tab cancellation-policy   /app/settings/notifications moved in   /app/settings/alerts moved in   /app/settings/integrations moved in, absorbs adapt /app/settings tab brand-settings /app/integrations /app/custom-checkout-adapt

Nine routes, not one route with nine tabs. A group is deep-linkable, which is what makes Settings search useful and what lets an error banner on Home point at the exact group that needs attention. It also means the browser back button works inside Settings, which a tab index in component state does not give you. The three absorbed routes keep working as redirects, because pilot merchants have them bookmarked and support articles link them.

The route, and what the resolver returns

The leaf routes do not change. What changes is what they store: a placement holds its own copy plus any override it has explicitly taken, and nothing else.

Leaf routes, unchanged

/app/widgets/:templateKey   stores placement + copy 9 keys   stores overrides 0 to 8 groups   stores 48 settings /app/portal-settings/customize   stores shop content, nav, CTAs   stores overrides   tab widget, 33 settings /app/landing-pages/customize/:id/...   stores sections, hero, windows   stores overrides   colors / typography / layout 0 readers

One resolver, four layers, provenance returned

resolve(shop, surface, placementId)   => Record<key, { value, from }> 1 widget_templates.default_settings code 2 shop_settings.brand / .selling new 3 surface defaults reserved 4 shop_widgets / shop_landing_pages leaf from: "default" | "brand" | "selling"       | "surface" | "placement" nearest layer wins. nothing is OR-ed.

Returning the layer alongside the value is what makes the admin honest. Every control on both screens renders its INHERITED or OVERRIDDEN marker from from, not from a guess, and a storefront debug header can print the same thing. Today, answering "why is this widget purple" means reading four files and knowing which store a given reader picked. Three OR-ed reads disappear here: the three data-hide-* theme-block checkboxes and group_bundle_variants across both stores. An OR across two sources means one of the two screens is a decoration.
