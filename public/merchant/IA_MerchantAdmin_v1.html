2. Why this order

Three principles, applied in sequence. Because App Bridge gives a flat list with no headers, order is the only structural signal available, so it has to be derivable rather than memorised.

1

Data lineage, parent before child

You cannot have a subscription without a plan, or an order without a subscription. A 6-delivery prepaid contract is one row in Subscriptions and six rows in Orders, so the parent sits above its children.

2

Derived views sit under their source

Payment Reminders is Orders filtered to unpaid. Inventory is Orders summed by SKU and date, looking forward. Neither exists without Orders, so both follow it instead of competing with it.

3

Configuration sinks into Settings

Anything set once and revisited rarely goes inside Settings rather than beside daily work. That covers integrations, billing, policies, and the customer notification templates.

Why not order by how often a screen is opened. That was the first instinct and it is wrong here. Frequency is not a property a merchant can see, so the sequence has no visible logic and has to be memorised, and every new module reshuffles it. Lineage is derivable: understand that a plan produces a subscription which produces orders, and you can predict where anything new will land. When Try Before You Buy ships it goes inside Plans, because that is what it is, and nothing moves.
The fold becomes useful. App Bridge truncates the list with a "View more" control. Today that cut falls at an arbitrary point, so the hidden items are random. Under this order, whatever falls below the cut is Settings and Analytics, which nobody opens daily.

4. The three versions

Same lineage logic and the same naming in all three. They differ only in how much they collapse.

Version C quietly undoes two decisions already made. Orders with Forecast and Unpaid tabs is structurally the unified "Orders & Inventory" hub superseded in D2026-0727-04, just renamed. It also removes Payment Reminders as its own screen, which was locked twice. C is the tidiest list and that is a real advantage, but it wins on count by reversing considered decisions. Take it deliberately, not by accident.
One open call: the bell. An embedded app cannot add anything to Shopify's own top bar, so admin alerts need StackBack's own header row inside the content frame. That is persistent chrome on every screen, and it costs vertical space everywhere. The cheaper alternative is no bell: alerts surface as a card on Home, and anything urgent banners the screen it concerns, so a failed push banners Orders. Less discoverable, zero chrome cost. Needs confirming against App Bridge before it is committed.
